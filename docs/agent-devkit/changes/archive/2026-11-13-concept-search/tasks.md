# Concept search tasks

## Design
[Concept search: a ranked, indexed code search in the Files Search pane](design.md)

## Global Constraints
- Indexed set: the files `git_view::file_list` returns (`git ls-files -z --cached --others --exclude-standard`, sorted, deduplicated), each read through `git_view::file`; skip a file that call reports as not `text` (binary, non-UTF-8, missing, unreadable) or `truncated` (over 1 MiB), and a file it refuses because the path resolves outside the checkout. A full pass considers only the first `MAX_INDEXED_FILES = 20000` files of the sorted listing; a sync adds a file only while the index holds fewer than that.
- Chunks: at most `CHUNK_LINES = 40` lines and `CHUNK_BYTES = 4096` bytes, broken at a line boundary; a full window ends at its last blank line when that blank line is in the window's second half; each chunk after the first starts at `max(previous start + 1, previous end - CHUNK_OVERLAP + 1)` with `CHUNK_OVERLAP = 4`, and a chunk is created only while lines not yet covered remain; a line longer than `CHUNK_BYTES` is indexed truncated to its first `CHUNK_BYTES` bytes.
- FTS5 table: columns `path`, `idents`, `body`; tokenizer `porter unicode61`; `bm25` weights `path 2.0`, `idents 1.5`, `body 1.0`. An identifier token is a maximal run of Unicode alphanumeric characters and `_`; `idents` holds, in order of appearance and without deduplication, the words `split_words` yields for each token that yields at least two words, and nothing for a token that yields one word.
- Query: split with the same word splitter as `idents`; each word quoted as an FTS5 string; AND first, OR if AND returns nothing; the last word also matches by prefix; no searchable word shows `No searchable words` in the pane's error line.
- Results: at most `CONCEPT_RESULT_CAP = 50` chunks, best first, as `GitViewSearchMatch` (`path`, `line`, `text`); `line` is the first line of the chunk containing any query word as a case-insensitive substring, else the chunk's first non-blank line, else the chunk's start line; `text` is that line cut to `SEARCH_PREVIEW_CHARS`; when two chunks yield the same `(path, line)`, keep the better-ranked row and drop the other before the cap applies.
- Index file: `GOKO_HOME/search/<fnv1a64(canonical checkout path) as 16 hex digits>.db`, directory mode `0700`, file mode `0600`. `refresh`, `sync_changed`, `search`, and the file-name function canonicalize the checkout first. A `meta` table holds the canonical checkout path and `PRAGMA user_version` holds the schema version; a mismatch deletes and rebuilds the file. A `files` table holds `(path, size, mtime_ns)` for every listed file, skipped ones included; a removed file loses both its chunks and its `files` row.
- Only `refresh` creates, rebuilds, or deletes an index; `sync_changed` writes only to an existing, matching index; `search` opens an existing index read-only and never writes.
- Full pass (`refresh`): compare `(size, mtime_ns)`, re-chunk only new or changed files, drop the chunks of a file that has become skipped, commit in transactions of 100 files, SQLite WAL with a 5 s busy timeout. It starts when Concept mode opens (and when the checkout changes with the pane open in Concept) if none has finished for that checkout in this session, and before a query when none is running and the last one, whether it succeeded or failed, finished more than `REFRESH_INTERVAL = 10 s` ago; a failed pass therefore retries at most once per interval; a pass already queued or running for a checkout is never queued again for it, and each checkout keeps its own last-pass record.
- Sync (`sync_changed`): run `git --no-optional-locks status --porcelain=v1 -z --untracked-files=all` through `git_view::status` (so it never takes the `index.lock` that a `git add` or `git commit` by the user or an agent in the same checkout needs); take the distinct `path` and `orig_path` of every conflict, staged, unstaged, and untracked entry; re-evaluate only those paths: stat equal to the stored `(size, mtime_ns)` means nothing is read; a path that no longer exists loses its chunks and `files` row; otherwise read with `git_view::file` and re-chunk, or drop the chunks and record the `files` row when the file is skipped. No `git ls-files` and no stat of any other path.
- Query deferral: once a full pass has succeeded for the checkout in this session, each Concept query is preceded by a sync on the indexer thread; the query waits at most `SYNC_WAIT = 1 s`; on expiry it is answered from the current index and issued again when the sync finishes with an unchanged input; a sync failure answers from the current index with no error of its own; while no pass has succeeded (first use, or the last one failed) the query is answered immediately from the current index and issued again when a pass finishes. A sync is queued before a due full pass. A sync that is queued and not started serves every query issued before it starts; a running sync does not. A pass that finishes while a sync is pending does not issue the query again.
- Index writes (passes and syncs) happen on the indexer thread, never on the editor backend worker; the worker only runs `code_index::search`.
- Switching mode, in either direction, clears the pane's `results`, `error`, `query`, `pending`, and `searching` and re-arms the existing input for the new mode when it has at least `MIN_QUERY` characters. `⇧⌘F` puts a pane that is in Concept back in Content before it runs; the go-to-definition fallback does so only in the branch that shows the pane (no unique declaration), before it writes the query and results; a unique declaration, a stale reply, and a non-Files section leave the pane untouched.
- The search box is always visible in the Files toolbar on its own row under the file filter; there is no toggle button and no separate mode row. Its `Text | Context` switch is a radio group named `Search mode` that exposes the selected option; the box starts in `Text`, and the picked mode lasts for the app session across checkout switches (not saved across restarts). Placeholders are `Search text` and `Search by context`; the user-visible failure text is `Context search unavailable: <reason>`. In the code the modes stay `SearchMode::Content` and `SearchMode::Concept`.
- `files.search.open` means "the aside shows the results". It becomes true when a query of at least `MIN_QUERY` characters is issued or the go-to-definition fallback shows results, and false when the search box is cleared or shortened, when the file filter is edited, and on a checkout change. Editing the file filter keeps the search text, mode, and results; a pass or sync that finishes re-issues a query only while `open` is true. `⇧⌘F` focuses the search box, selects its text, and puts it in `Text` mode.
- Times kept in the state (the last finished pass, the sync deadline) are `f64` seconds on the app clock `State::clock`; `search::poll` takes `now` and `tx`.
- No change to `gokod`, `crates/protocol`, the `goko.db` schema or migrations, or any dependency.
- Content mode (`Req::Search`, `git_view::search`) behaves exactly as before.

## Tasks
### Task 1 — Word splitter, identifier words, chunker, and FTS5 availability
Files: `crates/app-core/src/code_index.rs::split_words`, `crates/app-core/src/code_index.rs::ident_words`, `crates/app-core/src/code_index.rs::chunk_text`, `crates/app-core/src/lib.rs` (register `pub mod code_index`).
Interfaces: produces `split_words(&str) -> Vec<String>` (lowercase words), `ident_words(&str) -> String` (the `idents` column text for one chunk), and `chunk_text(&str) -> Vec<Chunk>` where `Chunk` carries `start_line`, `end_line` (1-based, inclusive) and `text`; later tasks consume all three.
Change: pure functions, no I/O. `split_words` splits at non-alphanumerics and `_`, at a lowercase-to-uppercase change, between an uppercase run and a following uppercase-then-lowercase (`HTTPServer` → `http`, `server`), and at letter/digit boundaries. `ident_words` finds identifier tokens (maximal runs of Unicode alphanumerics and `_`), applies `split_words` to each, and joins with spaces, in order and without deduplication, the words of every token that yields at least two words. `chunk_text` applies the chunk rules in Global Constraints, including the overlap; text with no lines yields no chunks; truncation of a long line cuts on a `char` boundary.
Verify: `cargo test -p app-core code_index` with named cases: `ReconnectBackoff` → `reconnect`, `backoff`; `reconnect_backoff_ms` → `reconnect`, `backoff`, `ms`; `HTTPServer2` → `http`, `server`, `2`; `ident_words("fn reconnect_backoff_ms(x) { // retry backoff after ReconnectBackoff }")` → `reconnect backoff ms reconnect backoff` (the plain words `fn`, `x`, `retry`, `backoff`, `after` contribute nothing); `ident_words` of prose with no compound token → empty; 100 lines without blank lines → chunks 1–40, 37–76, 73–100; a 40-line file → one chunk; a 41-line file → chunks 1–40 and 37–41; a 40-line window with a blank line at line 30 ends at line 30 and the next chunk starts at line 27; a first chunk of one over-long line is followed by a chunk starting at the next line (no overlap, still advances); a 5 KiB single line → one chunk whose text is at most 4096 bytes and valid UTF-8; empty text → no chunks; an in-memory SQLite connection creates `fts5(path, idents, body, tokenize='porter unicode61')` and answers a `MATCH` query (proves FTS5 is in the linked SQLite).

### Task 3 — Ranked search over the index
Files: `crates/app-core/src/code_index.rs::search`, `crates/app-core/src/code_index.rs::match_expression`, `crates/app-core/src/code_index.rs::open_index` (add `ReadOnly`), `crates/app-core/src/git_view.rs::SEARCH_PREVIEW_CHARS` (make `pub(crate)`).
Interfaces: consumes Task 2's `canonical_checkout`, `index_path`, `open_index`, and Task 1's `split_words`, plus `GitViewSearch` and `GitViewSearchMatch`; produces `search(home, checkout, query) -> Result<GitViewSearch, BridgeError>` with `truncated` true when more than `CONCEPT_RESULT_CAP` chunks matched; Task 5 calls it.
Change: `open_index` in `ReadOnly` mode opens the index file read-only without creating, rebuilding, or deleting anything and returns no index when the file is missing or its `meta` path or `user_version` does not match; an unreadable or corrupt file returns `Err`. `search` canonicalizes the checkout, opens with `ReadOnly`, and answers an empty `Ok` when there is no index. It builds the match expression and runs the ranked query per Global Constraints (AND, then OR on an empty AND result, prefix on the last word, quoted words so FTS5 operators are inert), applies the `(path, line)` dedupe before the cap, and maps each hit to `GitViewSearchMatch` using the line rule. ### Task 6 — Indexer thread and events
Files: `apps/rune/src/editor/search.rs::Indexer`, `apps/rune/src/editor/search.rs::IndexEvent`, `apps/rune/src/editor/search.rs::run_pass`, `apps/rune/src/editor/search.rs::run_sync`, `apps/rune/src/editor/search.rs::apply_index_event`, `apps/rune/src/editor/state.rs::EditorState` (an `indexer` field built in `EditorState::new` beside `Backend`), `apps/rune/src/main.rs` (stop the indexer where `s.editor.backend.shutdown()` runs).
Interfaces: consumes Task 2's `refresh` and `remove_orphans`, Task 4's `sync_changed`, and Task 5's state; produces `IndexEvent { Progress { checkout_key, done, total }, Done { checkout_key, truncated }, Failed { checkout_key, message }, Synced { checkout_key } }`, `Indexer::request_pass(checkout, key) -> bool` (`false` when a pass for that key is already queued or running), and `Indexer::request_sync(checkout, key) -> bool` (`false` when a sync for that key is already queued and not started); Task 7 consumes them.
Change: `run_pass(home, checkout, checkout_key, stop, sink)` runs `code_index::refresh`, calls `sink(IndexEvent::Progress)` after every 100 files and `Done` or `Failed` at the end, and passes a `progress` callback that returns `false` once `stop` is set. `run_sync(home, checkout, checkout_key, stop, sink)` runs `code_index::sync_changed` and always ends with `sink(IndexEvent::Synced)`, whether the sync succeeded or failed, so a waiting query is never stranded. `Indexer` owns one named thread and a channel of two job kinds (pass and sync, each with the checkout path as the sidebar holds it and its `checkout_key`) served first come first served, plus a set of `checkout_key`s whose sync is queued and not started: `request_sync` inserts the key and queues the job only when the insert is new, and the thread removes the key before it runs that sync, so a running sync never absorbs a later request.
